2Executive Summary

PeoplePulse is a proposed web application that gives an HR team one place to keep employee records, process resignations and other separations, coordinate exit clearance, record exit feedback, and report on turnover and retention.

The product is designed for general business use. Departments, roles, approval chains, separation reasons, clearance checklists and exit interview questions are configuration data that each organization sets for itself. Nothing in the design assumes a particular industry or HR policy.

The system uses a Next.js and TypeScript frontend, a Go REST API, MongoDB for storage, and n8n for scheduled and event-driven notifications. The Go API owns all business rules, authorization and data integrity. n8n only schedules, formats and delivers messages.

The scope is sized for one software engineer. The minimum viable product (MVP) covers the twelve modules in this proposal at a deliberately modest depth, and the estimated effort is 75 to 101 development days before contingency. This is an estimate with stated assumptions, not a delivery commitment.

The proposal makes no claim that software reduces turnover. PeoplePulse is intended to make workforce changes visible, consistently measured and easier to administer, so that the people responsible for retention decisions work from better information.

3Project Background

Employee turnover touches several HR activities at once: keeping records current, processing a resignation through its approvals, recovering assets and access before the last working day, capturing why the person left, and reporting the pattern to management. In many organizations these activities are handled with a mix of spreadsheets, paper forms, email threads and unconnected software.

When that is the case, three things tend to be hard: knowing the current state of any one exit, calculating turnover consistently from month to month, and seeing patterns across departments or over time.

Status of these statements. The background and problems described in sections 3 and 4 are working assumptions drawn from the project brief. They have not been validated with a specific organization. Phase 1 of the roadmap includes validating them with HR practitioners, and requirements may change as a result.

6Proposed Solution

PeoplePulse is a browser-based application with four parts.

  • Web application (Next.js, TypeScript, Tailwind CSS, Recharts). The interface for HR staff, managers, clearance officers and, optionally, employees.
  • REST API (Go). The single authority for business rules, permissions, metric calculation and data validation.
  • Database (MongoDB). Stores every organization's data, with each document tagged by organization.
  • Automation (n8n). Receives signed events from the API, runs schedules, and delivers email notifications and reports.

Design principles

  • Configuration instead of assumption. Departments, roles, approval chains, separation reasons, employment types, clearance categories and interview questions are set by each organization.
  • One source of truth for rules. The Go API decides what is allowed and what is due. The frontend and n8n never decide business outcomes on their own.
  • Derived metrics. Headcount and turnover are calculated from employment dates, so figures can be recalculated and explained.
  • Honest numbers. Every rate is shown with its numerator and denominator. Where data is missing or the group is very small, the system says so instead of showing a figure.
  • Tenant isolation from the first commit. Every document carries an organization ID and every query is scoped by it, so a second organization can be added later without redesign.
  • Small enough for one engineer. No microservices, message brokers or visual workflow designers.

8Functional Requirements

All API paths below are relative to /api/v1. Every endpoint requires authentication unless stated, and every query is limited to the caller's organization. "HR" means HR Manager and HR Officer. Role names refer to the default roles; actual access is decided by permissions.

The term separation is used for any exit from the organization. A resignation is one type of separation. Section A explains why the model is wider than resignations alone.

User actionsChoose a period, filter by department, open the list behind any figure.

8.2 Employee Management

Feature descriptionMaintain employee records, including joining date, department history and employment status. This is the data from which headcount and turnover are derived.
User rolesHR creates and edits. Department Managers view their own department. Employees view their own record.
User actionsAdd, edit, search, filter, import from CSV, transfer between departments, view an employee's timeline.

The end date is set by completing a separation; direct correction needs HR Manager permission and is audited. Records are never hard-deleted. Validation rulesJoin date is required and at most one year in the future. Email format is checked. The line manager is an active employee of the same organization and not the employee themselves. CSV import is validated row by row; an error report is shown before anything is saved.
Expected outputsPaginated employee list, employee profile with timeline of joining, transfers and separation, import result report.

User rolesOrganization Admin and HR Manager edit. All roles can view names.
User actionsCreate, rename, set parent department, assign department head, archive, restore.

8.4 Resignation Management

Feature descriptionRecord and process separations. Employee resignations go through the organization's approval chain. HR can also record other separation types, such as termination, end of contract or retirement.
User rolesEmployees submit their own resignation. HR submits on behalf of an employee and records other types. Approvers act on steps assigned to them. HR Manager records involuntary separations.
User actionsSubmit, approve or reject with comment, withdraw before final approval, change the last working day, mark as completed.
Business rulesAn employee has at most one open separation. The approval chain is copied from organization settings onto the request at submission, so later setting changes do not affect requests in progress. The proposed last working day defaults to the submission date plus the configured notice period; HR may change it with a reason. Nobody can approve their own resignation. If a step's approver cannot be resolved, for example no line manager, the step goes to the HR Manager role. On final approval the employee's status becomes "serving notice" and the clearance checklist is generated. HR-recorded separations skip the approval chain but require a specific permission. The reason's category sets the separation as voluntary, involuntary or other.
Input fieldsEmployee, separation type, reason (from the organization's list), reason details, submission date, requested last working day, comments.
Validation rulesThe employee is active. The last working day is not before the submission date. A reason is required. A rejection requires a comment. Status changes follow the state diagram below; any other transition is refused.
Expected outputsSeparation record with status history, in-app notifications, audit entries, events for n8n.
Related APIGET|POST /separations, GET /separations/{id}, POST /separations/{id}/approve, /reject, /withdraw, /complete, PATCH /separations/{id}/last-working-day

8.5 Exit Interview Management

Feature descriptionRecord structured exit feedback for a separation, using the organization's own question template. Holding exit interviews is optional.

User actionsEdit the template, schedule an interview, record or submit answers, view an interview, view aggregated results.

Input fieldsTemplate questions (type: rating 1 to 5, single choice, free text; required flag). Interview date, interviewer, answers, overall notes.

8.6 Employee Clearance Management

Feature descriptionTrack the tasks that must be closed before an employee leaves, grouped by categories the organization defines, for example IT assets, finance, administration and work handover.
User rolesHR sees all clearances and can update any item. Clearance Officers and Department Managers update items assigned to them.
User actionsView assigned items, mark an item cleared, not applicable or blocked with remarks, add an extra item, override completion.
Business rulesThe checklist is created by the API when a separation receives final approval, copied from the organization's clearance template. Each item is assigned to a role, a named user or the employee's line manager. Items are due on the last working day unless changed. Clearance is complete when every item is cleared or not applicable. 8.13 Metric definitions

These definitions are implemented once, in the Go API, and used by the dashboard, the analytics screens and every report.

Shared terms

  • Headcount on a date is the number of employee records whose join date is on or before that date and whose end date is empty or on or after that date. An employee counts as employed on their last working day.
  • Average headcount for a period is the mean of the daily headcount over every calendar day in the period. Because headcount is derived from dates, this needs no stored snapshots. It is less sensitive to hiring or leaving at the start or end of a month than the common shortcut of averaging the opening and closing figures.
  • Separations in a period are completed separations whose last working day falls inside the period. Internal transfers are not separations.
  • Counted employment types. Each organization chooses which employment types count, for example whether interns or short-term contractors are included. The same choice applies to numerator and denominator.

Formulas

MetricFormulaAssumptions and notes
Monthly turnover rateSeparations in the month ÷ average headcount in the month × 100Calendar month in the organization's time zone. Example: 6 separations and an average headcount of 120 gives 5.0%.
Annual turnover rateSeparations in the 12 months ÷ average headcount over the same 12 months × 100Shown as a rolling 12 months or by reporting year. It is calculated directly, not by adding or averaging monthly rates. A part-year figure is labelled "year to date" and is not scaled up to a full year.
Department turnover rateSeparations from the department in the period ÷ average headcount of the department in the period × 100Uses dated department history, so an employee counts in the department they belonged to on each day. Transfers in and out are reported beside the rate but are not turnover.
Voluntary turnover rateVoluntary separations in the period ÷ average headcount × 100Category comes from the organization's reason list, for example resignation.
Involuntary turnover rateInvoluntary separations in the period ÷ average headcount × 100For example termination or redundancy. Reasons classed as "other", such as retirement or end of a fixed-term contract, are reported separately. Voluntary + involuntary + other = total.
Retention rateEmployees on the first day of the period who are still employed on the last day ÷ employees on the first day × 100People hired during the period are excluded from both figures. It is not calculated as 100 minus turnover; the two can differ when new hires leave within the period.
Average tenureCurrent staff: mean of (as-of date − join date). Leavers: mean of (last working day − join date).Shown in years to one decimal place, with the median beside the mean because a few long-serving employees can pull the mean up. Each employment period of a rehired person is measured separately.
Resignation trendCount of resignations per month, by submission date; and separately by last working daySubmission date shows when people decided to leave; last working day shows when headcount changes. Withdrawn and rejected requests are shown as their own series and not counted as separations.
Headcount trendMonth-end headcount, joiners, leavers, net change = joiners − leaversClosing headcount = opening headcount + joiners − leavers. The API checks this identity in tests.

Handling missing history and avoiding misleading figures

  • Analytics start date. Each organization records the earliest date from which its data is complete, meaning that everyone employed on or after that date has a record, including people who have since left. No rate is calculated for a period that begins before this date. The screen shows "Not enough data" with the reason.
  • Why former employees matter. If only current staff are imported, past headcount is understated and past separations are missing, so historical turnover would be wrong in both directions. The import screen explains this and asks whether leavers are included before the analytics start date is set.
  • Completeness checks. A data quality panel lists records that affect metrics: missing join date, end date before join date, separated status without an end date, no department on some days. Affected periods carry a warning.
  • No division by zero. If average headcount is zero the rate is shown as "n/a", never as 0%.
  • Small groups. When average headcount is below the organization's threshold (default 5), the rate is flagged and the counts are shown first. One leaver from a team of three is 33%, which is arithmetically correct and easy to misread.
  • Partial periods. The current, unfinished month is labelled "month to date" and excluded from trend lines by default.
  • Future-dated exits. Approved separations with a future last working day appear under "upcoming departures" and do not count in turnover until the date passes.
  • Counts with every rate. Every percentage is displayed with its numerator and denominator, and exports include both.
  • Corrections change history. Because metrics are derived, correcting a past date changes past figures. Each report shows when it was generated, and date corrections are audited. Frozen monthly snapshots are a possible later feature.

11.2 Frontend and backend communication

  • The frontend calls the API with JSON over HTTPS. A typed API client is generated from, or checked against, the OpenAPI description.
  • The frontend hides controls the user has no permission for, as a convenience. The API enforces permissions regardless of what the frontend shows.
  • Client-side validation gives quick feedback. Server-side validation is the authority.
  • Lists use page, pageSize, sort and filter query parameters and return { data, page, pageSize, total }.

11.4 MongoDB data flow

  1. A handler parses the request and passes a typed command to a service.
  2. The service checks permission and business rules, then calls repositories.
  3. Every repository method takes the organization ID from the authenticated context and includes it in the query filter. The ID is never read from the request body or URL.
  4. When an action changes several documents, for example final approval, the service runs them in one transaction: update the separation, update the employee, create the clearance, write the audit entry and write the outbox event.
  5. Analytics endpoints run aggregation pipelines over employees and separations and return computed figures with their counts.

    participant B as Browser

Figure 4. Sign-in, authorized request and token refresh.

  • The JWT carries user ID, organization ID and role ID. Permissions are loaded on the server, so a role change takes effect without waiting for long-lived tokens to expire.
  • Refresh tokens are single-use. Presenting a used token ends the whole session, which limits the damage of a stolen token.
  • Sign-out, deactivation and password change delete the user's sessions.
  • Authorization has two parts: the permission, such as separation.approve, and the scope, such as "own department" or "assigned to me".
  • A record that belongs to another organization returns 404, the same as a record that does not exist.

All errors use one JSON shape:

HTTP statusUsed for
400 / 422Malformed request / failed validation, with field details.
401 / 403Not signed in or token expired / signed in without permission.
404Not found, including records in another organization.
409Conflict with current state, for example an invalid status transition or a concurrent edit.
429Rate limit reached.
500Unexpected error. The response has a generic message and a request ID; details stay in the server log.
  • Application logs are structured JSON with request ID, user ID, organization ID, route, status and duration. They contain no passwords, tokens or exit interview text.
  • Audit logs are business records stored in MongoDB and are separate from application logs.
  • Frontend shows field errors next to inputs, a clear message for failed actions, and an error boundary with the request ID for unexpected failures.
  • n8n has an error workflow that reports failed executions to the API, where they appear to the Organization Admin.

12.3 Embedding and referencing

  • Referenced by ID: entities with their own life cycle and independent queries, such as employees, departments, separations and users.
  • Embedded: small, bounded data that is always read with its parent, such as approval steps, clearance items, department history and organization settings.
  • Copied at the time of the event: the approval chain, clearance template and interview questions are copied onto each record when it is created. The department and tenure at exit are stored on the separation. This keeps historical records and reports stable when settings or departments change later.

12.5 Validation and consistency

  • Two layers of validation. Go structs are validated in the API before any write. MongoDB $jsonSchema validators on each collection enforce required fields, types and allowed status values as a second line of defence.
  • Transactions. Actions that change several documents run in a multi-document transaction. This requires MongoDB to run as a replica set, including in development.
  • Concurrent edits. Updates include the expected version. If another user changed the record first, the API returns 409 and the user reloads.
  • Referential checks. MongoDB has no foreign keys, so the service layer verifies that referenced IDs exist in the same organization before writing.
  • No hard deletes for employees, departments, separations or audit entries. Records are archived or deactivated.
  • Dates. Timestamps are stored in UTC. Business dates such as join date and last working day are stored as calendar dates and interpreted in the organization's time zone.

12.6 Multi-organization isolation

  • One shared database with organizationId on every document is used. It is the simplest model to operate and adequate for the stated scale.
  • The organization ID comes only from the verified token. Repository methods cannot be called without it.
  • Every index starts with organizationId, so queries for one organization do not scan another's data.
  • Automated tests create two organizations and assert that every endpoint refuses access across them.
  • Integration endpoints used by n8n return data grouped by organization, and each event names its organization.

13.2 Secure communication

API to n8n (webhooks)

  • The API posts each event to an n8n Webhook node over HTTPS on the private network.
  • Each request carries a timestamp, a unique event ID and an HMAC-SHA256 signature of the timestamp and body, made with a shared secret. The workflow's first step recomputes the signature and rejects mismatches and requests older than five minutes.
  • Workflows ignore an event ID they have already processed, because the outbox may deliver an event more than once.
  • Payloads carry what is needed to write the message: record IDs, recipient addresses, names, dates and a link. They do not carry exit interview content or reason details.

n8n to API (REST)

  • n8n calls only /api/v1/integrations/* endpoints, using a service API key stored in n8n credentials and stored hashed in the API.
  • The key has its own narrow permissions: read due items, read report data, write delivery status. It cannot approve, edit or read anything else.
  • Calls by the service key are written to the audit log with actor type "integration".
  • The key and the webhook secret can be rotated without code changes.

n8n itself

  • The n8n editor is protected by its own login and is not exposed to the public internet where the hosting allows.
  • Stored execution data is pruned on a short schedule, because it contains names and email addresses.
  • Workflow definitions are exported to the repository so they can be reviewed and restored.

14Implementation Methodology

The project follows an iterative, phase-based approach suited to one engineer.

  • Phased delivery. Seven phases, each ending with working, demonstrable software or reviewed documents.
  • Short iterations. Work is planned in one-to-two-week iterations from a prioritized backlog, with a review with the project supervisor or stakeholder at the end of each.
  • Vertical slices. Each feature is built through database, API and interface together, so integration problems appear early.
  • API contract first. Endpoints are described in OpenAPI before the screens that use them are built.
  • Version control and CI. Git with short-lived branches. Every change runs linting, tests and a build.
  • Definition of done. Code reviewed by the author against a checklist, automated tests passing, permission and tenant-isolation tests included, audit entry written where relevant, documentation updated.

16Expected Outcomes

If the MVP is delivered as described, an organization that adopts it can expect the following. These are intended outcomes of using the system, not measured results.

  • One maintained record of employees, departments and employment history.
  • A visible status for every separation, with its approvals, last working day and clearance progress.
  • Turnover and retention figures calculated the same way every month, with the counts behind them.
  • Comparable figures across departments, with warnings where a group is too small to read much into.
  • Exit reasons and feedback recorded in a form that can be summarized.
  • Fewer manual reminders, because routine notifications are sent automatically.
  • An audit trail of who changed or approved what.
Limits of these outcomes. PeoplePulse reports on turnover; it does not reduce it. Any change in retention depends on the decisions and actions managers take with the information. Time saved and other benefits will vary by organization and have not been measured. If measurement is wanted, a baseline should be recorded before adoption and compared afterwards.

19Conclusion

PeoplePulse is a focused proposal: one system for employee records, separations, clearance, exit feedback and the turnover and retention figures that come from them. It is built on a consistent stack of Next.js, Go, MongoDB and n8n, with business rules held in one place and policies left to each organization's configuration.

The scope has been cut to what one engineer can build in an estimated 75 to 101 development days, and the proposal is explicit about what is assumed, what is deferred and what the system does not claim to do. The recommended next step is to approve Phase 1, in which the assumptions in this document are tested with HR practitioners and the open questions in Appendix A are settled before development begins.
